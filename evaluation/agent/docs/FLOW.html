The whole pipeline

The harness owns everything outside the agent: packaging, the one DiscoPoP profile per benchmark, and the verdict. The agent never grades itself — its own summary line is a log, not a result.

1

Harness: from a benchmark to one profile

DiscoPoP is not deterministic — the same profile explored twice gives different task patterns, and on some programs the explorer crashes on one attempt and succeeds on the next (T0.7). Nor is its verdict on a loop (B4, re-measured 26 Sep): on one unchanged profile its explorer reports textbook recurrences Do-All in 6 of 8 runs (TSVC s112) and 7–12 of 15 (s121, s212, s243, s244); the gate catches every one, but which regions arrive as Tier 1 (diagram 3) is a draw — and since every trial of a run copies one profile, a run-level one. B9 (fixed 26 Sep, on the server with B8 after E1c-v3.1): the accesses of a function called inside a loop iteration reached no part of the task graph, so a loop carrying a dependence through a callee was reported Do-All — every TSVC repetition loop, through pb_mix. So a benchmark is profiled once per run and every arm and trial starts from a copy of that profile; a crash is retried on the same profile and every retry is counted. So is a stall: over 166 profile draws the explorer needed a median of 3.5 s and at most 33 s, while 7 % of the draws never finished — at random, not on particular loops. One attempt is therefore limited and a stalled draw repeated: the harness's first explorer run of a benchmark gets 600 s (nothing to scale from); inside the agent, since 23 Sep, the harness sets --explorer-timeout to max(60 s, 10 × that benchmark's own explorer run) — TSVC 60 s — because in E1 stalls waited out at 600 s were a third of all trial time. Until 21 Sep the agent's own call had no limit at all.

Planning: which regions are worth an attempt, and in what order

Every function, loop and basic block DiscoPoP recorded is a region. A region is ranked by the time parallelising it would save, ΔT = T · f · (1 − 1/(P·e)), where f is the share of runtime still sequential in it. With P and e fixed this orders regions by f; ties go to the outermost region — except that a loop beats the function containing it when it carries at least 90 % of the function's measured time (so main does not head every queue).

Where a loop's iteration count comes from (Fix 88, 21 Sep). Not from DiscoPoP's loop_counter_output.txt: that file pairs counts with the wrong loops — 82 % of 337 loops over 41 archived profiles; an outer loop of 7 around two sibling loops of 998 is reported as 6986 / 6986 / 1000. The agent sums the BGN loop markers of dynamic_dependencies.txt, which is what DiscoPoP's own explorer reads, so the DiscoPoP-alone baseline was never affected; the counter file remains the fallback for a loop without a marker (code a fast refresh never ran). The wrong counts had fed the workload proxy and the "N iterations" in every prompt header (a recorded limitation of pilot4 and E10).

One model call

The system prompt is generated from the gate that is really configured (is speed judged, how many inputs, exact or numeric comparison, is the schedule matrix on) and from the evidence sections that are really sent, so the configured facts are right. What it said about SPEED was not, until D40 (26 Sep): with DiscoPoP writing the pragmas it named “speed against the same build on one thread” — Phase B's per-pragma check — and never that the program must beat the ORIGINAL, which is what decides (Settle, the harness); with --llm-pragmas it named only the one-thread half of the gate's two conditions. Since D40 (--judge-as-shipped) it states the deciding comparison in the words the twins and the model alone read, and a slow rewrite is reverted with the measured ratio. Its promise of feedback “after a failed attempt” holds for Phase A's checks and D40's; what Phase B and Settle find is not fed back. It is identical for every call of a run, which keeps the provider's prompt cache warm. Format problems are re-prompted without charging the region's budget.

6

The quality gate

Two tracks. A rewrite with no pragma is a sequential-to-sequential change and is judged on a sequential build. A patch that carries a pragma is judged on concurrency evidence — the sanitizer, then the schedule matrix — with the output comparison as the end-to-end check. No single stage concludes "correct"; the verdict is their conjunction, and the evidence of each is recorded. For a project every build below is the whole staged program with the candidate in place of the one file under test.

After a rewrite passes the gate

The rewrite is written to the real file, the profile is brought up to date, and only then is it decided whether the rewrite stays. Who decides depends on who wrote the pragmas. Since D23 the model does not write them by default, so the usual path is the second one: DiscoPoP must now find a usable pattern in the lines that changed, and a rewrite it cannot use is reverted. Where the model did write them (--llm-pragmas, opt-in per experiment), the gate has already judged the parallel code and the refreshed profile only relocates the queue.

Two things on this path changed on 21 Sep. The runtimes are now re-measured after every kept rewrite, not only when a deeper restructuring level was coming — Phase B ranks the regions a rewrite created on every run, and while the re-measurement was gated on a deeper level it never ran at the default --restructure-depth 0, so those regions arrived unmeasured and --min-runtime-share dropped every one of them (Fix 86). The re-measurement itself then had to be made honest: DiscoPoP's hotspot detection accumulates region ids and averages over runs, so re-measuring into the same directory reported the OLD program's lines, halved, with nothing for a created region (Fix 87 — the directory is cleared first). Since D29 the fast refresh re-measures as well — it exists to skip the instrumented run, and this is one native-speed run; without it E3's fast arm alone could not rank the loops a rewrite created. Every refresh is recorded as what it actually was ([refresh] kind=fast, full or fallback; per trial refresh_fallback), so a fast-refresh trial that fell back to a full re-profile is visible in E3's read-out: 0 of 108 so far. And where a model-written pragma sits on a loop DiscoPoP has also claimed, the two are now timed against each other and the faster is kept (Fix 85) — that step needs both --llm-pragmas and --require-speedup, so by default it never fires.

Phase B: DiscoPoP's pragmas, once, from a measured profile

Phase A leaves DiscoPoP's pragmas out of the source so that line numbers and the profile stay valid while code is still moving. Phase B then applies every pragma that survives, largest predicted saving first, each one re-derived against the file as it stands. Nothing found here reaches the model — its attempts are over; since D40 a kept rewrite's own pragmas were already judged, in Phase A, while it could still act (their gate verdicts are cached, so Phase B does not pay again).

Since D33 (Fix 93, 23 Sep) a pragma that is safe but slower ALONE is deferred, not dropped. Each pragma is timed against the state before it; when a rewrite splits one loop into two or three, each alone can lose (0.6–1.1×) while all together win (2.5–4×) — one parallel loop next to a sequential one does not pay. In E1 that dropped the winning set in 7 of 18 such trials (replayed: FASTER 1.49–3.00× under the harness). The deferred pragmas of each file are now applied together, re-checked for safety as a set, timed against the state before them, and — if the set pays — members are removed one at a time while removing one does not slow it down. What is kept is ONE change-log entry, so Settle keeps or drops the set as a unit. A lone deferred pragma is dropped as before; a pragma that pays alone takes exactly the old path.

Settle: the only step that judges the finished files

Speed, since Fix 89 (22 Sep): the finished file is timed against the original, interleaved — the same measurement and threshold Phase B applies to each pragma — instead of alone against the reference time captured when the run began. On E1's shared host that opening reference was minutes old by the time Settle ran; the 15 programs Settle dropped this way in E1 were rebuilt and re-judged by the harness and were indeed slower, so the change is one of method. Where a rewrite's cost is judged: nowhere before this step. Phase A accepts a pragma-free rewrite on output alone, because a buffer that only pays off with the pragmas is the normal case; Phase B measures each pragma against the state before it, not against the original. So a rewrite that copies the whole array on every repetition (E1: memcpy, or malloc/free per repetition) reaches Settle with its pragmas accepted and is dropped here — correctly, after the trial's budget is spent. Since D40 (agent v3) such a rewrite is judged in Phase A instead — reverted with its measured ratio while the region's budget can pay for another attempt; Settle stays the final check on the finished file, and nothing it finds is fed back. A bound on the rewrite's sequential cost in Phase A was proposed (D31) and withdrawn on a measurement: the expert restructurings themselves run 1.0–2.3× slower sequentially, so no such bound separates a bad rewrite from a good one. What would recover the trial is a retry after Settle's verdict, with it as feedback (D31-b, proposed). From class A: Settle compares the finished program with the ORIGINAL, never with DiscoPoP's own program — so on code DiscoPoP already parallelizes, a slower parallel program survives (vpvtv, 0.58× of DiscoPoP alone), and a repair that ends below the original falls back to the original rather than to DiscoPoP's pragma (s000, lost). A structural fix (skip regions whose loops carry DiscoPoP patterns, Fix 90) was reverted before it ran: in class R those patterns are false positives the gate rejects, and the rule would have blocked 11 of 18 class-R loops. Since D32 (Fix 94, 23 Sep) there is a floor: before Phase A the agent builds DiscoPoP's own gated program — Phase B and Settle on the original, exactly what the DiscoPoP-alone arm delivers (its console in floor/floor.log) — and after this step the agent's finished program is timed against it, paired; if it is slower, DiscoPoP's program is shipped. On E1's class A that turns vpvtv (worse) and s000 (lost) into equal; on class R DiscoPoP alone keeps nothing, the floor is the original and nothing changes. The DiscoPoP-alone arm itself (--budget 0) is its own floor and skips it.

Every gate before this judged one candidate patch on a temporary copy. What ends up on disk is a reconstruction — the surviving changes re-applied onto the originals — and it has to earn its own verdict, with the same tolerance and stress settings the earlier gates used.

Harness: the verdict on a trial

The harness builds the original and the final source itself, at the per-kernel verification size (T0.1), runs them at several thread counts with repeats, and compares digests and a full dump of the results on the default and on a perturbed input. The order of the checks below is the order in the code: an instrument that was tampered with is caught before any number is believed.

Unusable programs are results, not lost trials (H13, the author, 24 Sep). The per-trial outcome is unchanged; the read-out (main_comparison_stats.py --three-way) counts, for every arm alike, a program that is BROKEN, racy (the gate's race stages run afterwards on every program no gate saw, race_check.py), correct but slower than the original (parallel or not — a rewrite with no pragma is timed like any other), or does not compile (the harness built the original and failed only on the final program) — failures of the code under test only — and tests, loop by loop, whether the agent ships fewer of them than the model alone and than its twin. A program that touched the harness code has no valid measurement: its own row, never counted, even when it does not build (the author, 25 Sep). E1c, the first test: the agent 0 of 90, the model alone 46 of 90 (p = 0.0004). E2: every agent arm 0 of 90; the twins 71 and 73, twin_dp 70 (the agent fewer on 18 of 18 loops against each twin, p < 0.0001).

What the verdict can and cannot be trusted with (21 Sep). (1) The dump must hold results only. The LULESH package emitted LULESH's three symmetry differences — mathematically equal energies, subtracted: rounding residue that a correct parallel version moves by 25 % — and the harness called LLNL's own OpenMP release BROKEN while every energy agreed to 2e-16. The agent's gate reads the digest and would have accepted the same program, so the trial would have been scored unsafe. Fixed; and from now on every package must accept its own expert version before it is used (T0.14). (2) The ceiling of the default arm is measured, not assumed (T0.13): the expert restructuring with its pragmas stripped, --budget 0 — DiscoPoP's pragmas on it are kept on 16 of 18 class-R TSVC loops; the other two need a pragma DiscoPoP cannot write. (3) A correctness verdict at four threads is provisional: the expert hotspot pragma passes every check on a laptop.
