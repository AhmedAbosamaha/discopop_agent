The fast-refresh experiment

After the model rewrites a loop, the agent profiles the whole program again: it compiles it with DiscoPoP's instrumentation, runs it, and lets DiscoPoP analyse the run. The fast refresh skips the run. It compiles only, and carries the dependences of the last run over to the new code. For the lines the model just wrote there is then no measurement. The second idea is to ask the model itself which dependences those lines have.

The 22 lost wins are nearly all one thing: a reduction the model created — 20 of the 22. The model rewrites the loop so that DiscoPoP can see a minimum, a maximum or a sum:

before the rewrite     if (a[i] < x) { x = a[i]; }
the model's rewrite    x = fmin(x, a[i]);

after a full profile   #pragma omp parallel for reduction(min:x)      passes every check; the rewrite is kept
after a fast refresh   #pragma omp parallel for firstprivate(x)       would lose the result; refused; the rewrite is thrown away

After the fast refresh nothing was ever measured on the new line. DiscoPoP therefore sees a loop without any dependence and treats x as an input. The agent's own check on the clauses refuses that pragma in all 20 cases. 13 of the 22 are rewrites that a trial shipped as its result.

The 2 kept only after the fast refresh. One is a loop that records the position of the largest element: with two equal largest elements two threads could write the position at once, and the test data hold only one largest element, so no check can see it. The full profile reports no parallel loop there. The other looks like a correct pragma that the full profile blocks. Both are my reading of the code, not checked by a run; neither was shipped by its trial.

The 34 with other pragmas. In 27 the only difference is a shared(...) clause that the full profile writes and the fast refresh leaves out. OpenMP shares those variables anyway, so the programs are the same. Counted that way 31 rewrites differ, not 58.

No time is saved on these loops. One fast refresh takes 1.54 s against 1.75 s. But after it DiscoPoP offers many more pragmas — 1,099 against 634 — and checking them costs more than the skipped run saved: 1,758 s against 1,730 s in all.

Your written-down claim that the fast refresh changes no decision is refuted by the test fixed before the run: p = 0.0003, and at most 0.018 when it is counted with every other test of the thesis. With the 27 counted as the same it is still refuted as a single test (p = 0.001), but not within that whole family (0.053).

Why — and it is not the model's mistake

In all 12 damaged rewrites the model said that the loop is independent, as the full profile does. What damages the loop is a dependence the model reported for another loop. One of them:

12        memcpy(a_copy, a, LEN_1D * sizeof(real_t));
14        for (int i = 0; i < LEN_1D-1; i++) {           the loop that should become parallel
15            a[i] = a_copy[i] * c[i];

the model's answer      LOOP 10 RAW a 15 12      true: each repetition reads what the last one wrote

My way of adding the model's answer writes the dependence without saying which loop carries it, and DiscoPoP then counts it against the inner loop too. The answer was right; the adding is what breaks it.

The opposite direction: letting the model delete dependences

Asked on 20 rewrites about 41 dependences that block a loop: the model called 16 real and 19 not real (6 unanswered, which count as real). All 19 are in four rewrites of one loop, and reading the code its reasons are right. No decision changed on any of the 21 rewrites.

Your third claim — deleting is unsafe, adding is not — is not supported by this measurement: neither direction produced a keep the full profile would not make (0 and 0). The reason is structural: after a fast refresh there is almost nothing to delete (21 of 599 rewrites), and never on the rewrites the refresh gets wrong. The claim stays an argument about the design; it is not a measured result.

What it means

  • The fast refresh is not adopted — the plan's rule for this outcome. It loses wins, saves nothing on the loops, and 1.5 to 7.5 % of a trial where the run is long.
  • The model can report the dependences of its own code — it named the missing one for every reduction it built. That part of your second claim holds.
  • The report as built does not make the fast refresh usable: it repairs 28 decisions and damages at least 60. On the whole set your second claim fails.

The instructions

You are reviewing DiscoPoP's STATIC dependence analysis of C/C++ code.

Static analysis is over-approximate by construction: it reports a dependence
whenever it cannot PROVE the absence of one.  For code that was just
rewritten there is no profiling data to settle the question, so each
reported dependence is either real or an artefact of what the analysis
could not prove.

Every dependence below is one DiscoPoP names as the reason it will not
parallelize a loop, and every one comes from STATIC analysis — anything it
actually observed running is not shown to you and is not up for discussion.
You are given the variable and the loop it blocks.
Decide:

  REAL      the dependence genuinely occurs at run time — a value written in
            one iteration is read in another, so the loop cannot run its
            iterations in parallel
  SPURIOUS  it cannot occur — the accesses are to disjoint memory, or they
            never overlap between iterations, or the "dependence" is on a
            location each iteration writes before reading (which
            privatization handles)

Two things are already handled and will not be asked about, so do not reason
as if they were the issue: the loop's own induction variable, and variables
declared inside the loop body.

Judge only what the code shows.  If you cannot tell, answer REAL: a
dependence wrongly called spurious can make a sequential loop look parallel,
while one wrongly called real only costs a missed parallelization.

Answer with one line per dependence and nothing else:

    <number>: REAL|SPURIOUS - <at most 15 words of reason>
