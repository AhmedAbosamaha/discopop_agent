How the loops were chosen

The rule was written down before DiscoPoP or a model touched any of them: every loop of the suite's two sections reductions and search loops that is not in the main set already and can be measured soundly. DiscoPoP alone, without a model, then sorts them: a loop it parallelizes itself is a control; a loop it leaves unchanged is under test.

That gives six loops under test and one control, not the eight I named. I named the eight from their headings before reading them.

Left outWhy
s13110Its text is s3110's, statement for statement. One loop, not two.
s3110It searches a two-dimensional array that nothing changes between repetitions, so a program could compute the answer once and reuse it — the weakness we just closed on s341. It is also far too small to time (256 × 256 elements).
s332It stops at the first element above a threshold. To make its result move between repetitions the match would have to sit at the start of the array, and then there is nothing left to search.
s31111No loop over the data inside a repetition.
s312, s317A product over the whole array is zero or infinite at the size we measure at.
s3111Packaged and measured, then left out. DiscoPoP does offer its pragma for this sum, and the agent's output check refuses it: a sum added in parallel differs in the 15th digit, and on this loop the check compares byte for byte. No setup can win it, whoever writes the pragma.

The six loops under test

DiscoPoP alone leaves each of them unchanged.

Corrected after the run. This page said that five of them need a pragma DiscoPoP cannot write. That was wrong, and it was my error. DiscoPoP can write a pragma for a maximum, but only when the loop is written as x = fmax(x, a[i]). It does not recognise the loop as the suite writes it, if (a[i] > x) x = a[i];. In the run the model often rewrote the loop into the form DiscoPoP recognises, and DiscoPoP then wrote the pragma itself. The sixth loop is a sum for which DiscoPoP offers nothing as written.

s315.c

The largest element and the first position that holds it. What a right answer needs: no single clause: each thread keeps its own value and position, and the pairs are merged under a lock.

#include "data.h"

real_t kernel_s315(void)
{
    real_t x, chksum;
    int index;
    for (int nl = 0; nl < iterations; nl++) {
        x = a[0];
        index = 0;
        for (int i = 0; i < LEN_1D; ++i) {
            if (a[i] > x) {
                x = a[i];
                index = i;
            }
        }
        chksum = x + (real_t) index;
        dummy(a, b, c, d, e, chksum);
    }
    return index + x + 1;
}
  • DiscoPoP alone, three runs without a model: unchanged in all three.
  • The reference parallel version is correct and 10.62× faster at 12 threads.

s318.c

The largest absolute value at a stride, and the first position that holds it. What a right answer needs: the same pair per thread; the running position k first has to be written as i * inc.

#include "data.h"

real_t kernel_s318(void)
{
    int k, index;
    real_t max, chksum;
    for (int nl = 0; nl < iterations; nl++) {
        k = 0;
        index = 0;
        max = ABS(a[0]);
        k += inc;
        for (int i = 1; i < LEN_1D; i++) {
            if (ABS(a[k]) <= max) {
                goto L5;
            }
            index = i;
            max = ABS(a[k]);
L5:
            k += inc;
        }
        chksum = max + (real_t) index;
        dummy(a, b, c, d, e, chksum);
    }
    return max + index + 1;
}
  • DiscoPoP alone, three runs without a model: unchanged in all three.
  • The reference parallel version is correct and 20.58× faster at 12 threads.
  • That factor is not parallelism alone: the reference also replaces the running position and the jump by a plain loop.

What a model does not see

  • The data. The arrays are filled in a file outside the package. For these loops the values are arranged so that the answer changes from one repetition to the next — otherwise a program could compute it once and reuse it.
  • The stride of s318. inc is 1, set outside the package, as the suite's own driver passes it.
  • One thing removed from s315. The suite's function fills the array itself before its repetitions. That is data set-up, so it is done outside the package here; the two lines are not in the file.

s341: the file is unchanged, the data are not

What the checks without a model found

  • The packages are the same on both machines: 9 of 9 pass the generator's checks on the Mac and on the server, and all 45 files have the same digest on both.
  • Every repetition is necessary: for each package, a variant that skips repetitions and one that reorders them both change the output, on both inputs.
  • Every loop can be timed: 1.5 to 5.5 seconds for the serial loop at the size we measure at.
  • Every reference is correct and faster by the harness's own verification.
  • DiscoPoP writes nothing on the reference either: given the reference of each of the five extreme-value loops with its pragmas removed, DiscoPoP writes none.
  • The agent's checks do not wrongly refuse the plain right pragma on the three one-clause loops (asked directly, without a model).
  • s341 is the loop DiscoPoP saw before: on the new data its view is the same in two runs.

Still open

  • A limit of the agent's output check, found here. It allows a numerical difference only as large as six builds of the original disagree among themselves. Where they agree exactly, a correct parallel sum is refused for a difference in the 15th digit (s3111). The harness's own verification accepts the same program. Whether the check should allow for a reordered sum when the pragma is a sum reduction is your decision; nothing is changed.
