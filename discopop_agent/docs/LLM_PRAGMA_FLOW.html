DiscoPoP agentic controller · --llm-pragmas

Who Writes the Pragma

By default the LLM restructures and DiscoPoP annotates, so a rewrite is kept only if re-profiling makes the profiler find something. Under --llm-pragmas the model writes the #pragma omp in the same edit — and the rewrite is judged on its own merits: clauses, sanitizer, output from the parallel build, clock.

Where the flow forks

Everything before Phase A is unchanged: profile, rank, collect evidence. The fork is one question asked of the model's diff — does it carry a pragma? — and it decides who gets to say whether the rewrite was worth making.

The gate, both ways

Most of this was already built. validate() keys the -fopenmp build, ThreadSanitizer and the timing on the diff containing a #pragma omp, so three stages that were structurally dead for an LLM rewrite come alive the moment the model writes one. Only the first row is new code.

The division of labour is unchanged, only relocated. The LLM still exposes parallelism and a measurement still decides whether it was worth it. What moved is where that measurement happens: from “re-profile, then time whatever DiscoPoP found” to “time the thing the model wrote.” --require-speedup remains the switch for whether the question is asked at all.

The one genuinely new check

A pragma the model wrote gets the same two static rules the agent already applies to DiscoPoP’s generated clauses — because clauses go wrong in the same two ways whoever writes them. The rules run against the patched text: the loops being annotated do not exist in the file yet.

Rule 1 · not in scope

A name declared inside the loop body is already per-iteration and cannot appear in a clause at all. This one fails loudly — use of undeclared identifier — but failing it in a static read costs nothing instead of a build.

Rule 2 · the silent one

A name the loop writes and later code reads must never be private or firstprivate: those discard the writes, so the later read sees a stale value and the program keeps running with a wrong answer. No compiler, sanitizer or output check sees this.

Arrays, not pointers

Rule 2 now also counts arr[i] = …, but only when arr is declared with array storage. private on an array copies the array and loses the writes; private on a pointer copies the pointer and the writes still land. Treating them alike would reject correct pragmas.

Then what is the re-profile still for

It stops being the arbiter and becomes bookkeeping — but it is not optional bookkeeping. It costs the same ~15 s it always did.

  • Line numbers. Every candidate still queued was located by line. One accepted rewrite moves all of them, and regions are re-matched across the re-profile by content fingerprint.
  • New candidates. A rewrite often exposes loops that did not exist before; those enter the queue at depth + 1.
  • Phase B’s raw material. patterns.json and the generated patches are what Phase B annotates from, for every region the model never touched.
  • Not the verdict. DiscoPoP’s opinion of a self-annotated rewrite is logged and otherwise ignored. If the re-profile fails outright, the rewrite is kept — it passed the whole gate — and Phase B is skipped for the run, because no profile then describes the file on disk.

Two places downstream had to learn about it

Phase B · do not double-annotate

The instrumented build carries no -fopenmp, so the re-profile reads the annotated source as sequential — correctly — and then proposes a pattern for a loop that is already parallel. Phase B now checks the line above the loop it is about to annotate and leaves it alone.

Settle · not an orphan

A rewrite is normally dropped at the end unless a kept pragma targets a region it exposed. A self-annotated rewrite is its own justification. It can still be dropped when the finished file fails its final gate — but only after every DiscoPoP pragma has been dropped first.

The sanitizer had to be fixed first

The first live attempt failed at TSan three times in a row, on code that was correct. There is no libarcher.dylib in this machine’s LLVM 19 / libomp install — Homebrew’s runtime carries no ThreadSanitizer annotations, so TSan sees none of OpenMP’s synchronization and reports a race between any two parallel regions that touch the same data.

Proof, not inference: a program whose second parallel for reads what the first one wrote — indices reversed, so a different thread reads each element — is bit-identical over 20 runs at each of 1/2/4/8/16 threads, and TSan calls it a data race.

the discriminator, from three real TSan reports
programracing framesverdict
odd-even sort .omp_outlined.2 line 12 vs .omp_outlined line 7 artefact — different regions, barrier between
two-region toy .omp_outlined.2 line 13 vs .omp_outlined line 11 artefact — same reason
naive parallel bubble .omp_outlined line 6 vs .omp_outlined line 6 real — one region, genuinely concurrent

The cause is one line in Homebrew’s own formula: -DOPENMP_ENABLE_OMPT_TOOLS=OFF. That flag is what builds archer — the tool that subscribes to the OpenMP runtime’s OMPT callbacks and calls TSan’s AnnotateHappensBefore on every barrier. Turned off, the chain runtime → OMPT → archer → TSan breaks at the third link and TSan never hears about a single barrier.

Fixed at the root. The runtime side needed nothing — Homebrew’s libomp already has OMPT compiled in, it looks up ompt_start_tool and honours OMP_TOOL_LIBRARIES. Only the tool was missing, and it is one source file: discopop_agent/tools/build_archer.sh fetches openmp/tools/archer/ompt-tsan.cpp at the LLVM tag matching the installed libomp and builds it. find_archer() picks it up, _tsan_env() loads it, and the banner says which mode a run is in.

  • The fallback stays. On a machine with no archer, _is_omp_barrier_false_positive reads the artefact off the report: every racing access inside an .omp_outlined* frame but in different outlined functions means a barrier separates them. Same outlined function on both sides is one region, and is left alone. Disabled when the code uses nowait or tasks.
  • Nothing is accepted on that heuristic. It re-runs with the race check off, and the patch must still reproduce the output exactly — which is what caught the first attempt’s real defect, an odd-even sort left at n-1 phases.
  • ignore_noninstrumented_modules=1 is set only alongside archer. On its own it suppresses reports from inside the uninstrumented runtime without supplying the ordering that makes them wrong — hiding real races along with the artefacts.
  • A parser bug it uncovered. TSan capitalises only the first access (Write of size 4…) and writes the second as Previous write. Matching on "Read"/"Write" saw one of the two, quietly weakening every rule phrased as “every racing access”.
  • Phase A never ran the re-check at all. It called validate() directly, while the re-verification lives in _validate_cached. Harmless while LLM rewrites carried no pragmas; fatal the moment they did.
