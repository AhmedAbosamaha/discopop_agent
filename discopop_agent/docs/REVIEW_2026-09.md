# Full agent review — September 2026

Written while reading every module in pipeline order (`run.py` → `plan/` → `evidence/` →
`llm/` → `phases/` → `gate/` → `profiling/` → `pragmas/` → `sources/`). Each finding states
what the code does, why it matters, the evidence, and its status. Severity: **H** can change
a result, **M** wastes work or hides information, **L** is hygiene.

## Findings

|---|---|---|---|---|
| F1 | H | `plan/regions.py` `_load_patterns` | The pattern index keeps the FIRST pattern per `start_line`/`node_id`, and `patterns.json` lists `task` before `do_all`/`reduction`. A task pattern therefore hides a loop pattern on the same line. Measured on T0.6: 44 lines across the suite where a non-applicable task entry hides an applicable `do_all`; 11 lines carry both `do_all` and `reduction`, of which only the first is seen. So far all 44 lie in `main`, which is why no kernel result was affected — but nothing guarantees that. | fixed — Fix 71 |
| F2 | M | `phases/phase_a.py` COMMIT | When a self-annotated rewrite is kept but the re-profile fails, `del candidates[i:]` runs with empty `rebuilt`, so every remaining region is dropped silently — not logged, not counted as skipped. | fixed — Fix 72 |
| F3 | M | `phases/phase_a.py` | The profile snapshot (`_snapshot_profile`, a copy of all of `.discopop`) is taken for every Tier-2 region before the first model call, whether or not any attempt ever passes the gate. On LULESH the profile is 7.1 GB. It is only needed once a candidate has passed. | fixed — Fix 72 |
| F4 | M | `phases/phase_a.py` | If `_apply_to_source` fails on the real file after the gate passed on the temp copy, the run continues: it re-profiles the unpatched source and records the rewrite as accepted. | fixed — Fix 72 |
| F5 | L | `run.py` baseline | The `BEAT/MATCHED/BELOW` verdict compares against DiscoPoP patterns from ONE explorer draw; T0.7 showed that draw varies. The harness ignores the verdict, but the log presents it as a fact. | open (log wording only; the harness ignores the verdict) |
| F6 | **H** | `gate/validate.py` stage 3b + `evidence/blockers.py` | **The `dependences` stage judges a REWRITE by the ORIGINAL loop's dependences.** Phase A passes the original region's span; `load_prevented_deps` matches any blocker whose loop merely OVERLAPS that span; a DYNAMIC blocker is a hard fail. But a region reaches the model precisely because it has such a blocker, and removing it is what the rewrite is for. **Proven on Floyd–Warshall** (core ten, group B): the correct parallelisation — copy row k and column k, `parallel for` on the i loop — is ThreadSanitizer-clean, agrees over 7 thread/schedule configurations and reproduces the output exactly on both inputs, and is rejected at `dependences` ("DiscoPoP OBSERVED 3 loop-carried dependence(s)…"); with the stage not consulted it passes. Whether the blockers exist at all is an explorer draw (seidel-2d: 2 of 6 profiles), so the verdict is also random. The module's own docstring says the rewritten-loop case "surfaces as no-data"; it does not, because the lookup is by line range and the original loop's lines still hold data. | fixed — Fix 64 |
| F7 | M | `gate/validate.py:468`, `phases/settle.py:72` | The barrier false-positive heuristic has a guard — it must not fire when the patch uses `nowait` or tasks, which genuinely remove the barrier — but both callers invoke `_is_omp_barrier_false_positive(diagnostic)` without the `code` argument, so the guard is dead. A real cross-region race in `nowait` code would be re-judged with the race check off. Only the feature test passes the code. | fixed — Fix 66 |
| F8 | **H** | `gate/schedules.py` | **The schedule matrix does not vary the schedule.** It sets `OMP_SCHEDULE`, which OpenMP applies only to loops declaring `schedule(runtime)`; a plain `#pragma omp parallel for` ignores it. Measured: the iteration→thread map of a plain loop is identical (`0000111122223333`) under `static`, `dynamic,1` and `guided`, and changes only with `schedule(runtime)`. So the `T4/dynamic,1` and `T4/guided` entries in every `evidence["schedules"]` list are repeats of the static run, and the stage's power to expose an order-dependent loop is far below what it reports. `dynamic,1` is the configuration that interleaves neighbouring iterations across threads — exactly what reveals a recurrence. | fixed — Fix 65 |
| F9 | **H** | `phases/settle.py` `_check_final_source` | **Settle re-judges the finished file byte-exactly.** It calls `validate()` without `noise_floor` (nor `stress_threads`), so the default 0.0 applies and outputs must match to the last bit. Phase A and Phase B pass the measured floor. A reduction accepted there under numeric tolerance therefore fails Settle's correctness stage and is dropped, and with nothing else left the whole run is reverted. Proven on `calib/dotprod`: the same `reduction(+:acc)` patch passes with the floor (mode `numeric`) and fails at `correctness` when called as Settle calls it. | fixed — Fix 66 |
| F10 | **H** | `run.py` + `gate/equivalence.py` `numerical_noise_floor` | **The numerical noise floor is calibrated on the default input only, but applied to every check input.** When the default input is rounding-free — values exactly representable in binary, as integer-derived initialisations often are — every build variant agrees, the floor is 0, and the perturbed input (`--check-input 7`), which does round, is then compared byte-exactly. Proven on `calib/dotprod`: floor 0 on the default input ("6 build variants agreed exactly"), 1.0e-12 on the seeded input; the textbook `reduction(+:acc)` is rejected at `correctness` with the first and accepted with the second. The floor has to be the maximum over all inputs the gate will compare. | fixed — Fix 66 |

## Prompts and evidence — judged on a real rendered prompt

The complete system and user prompt for `kernel_floyd_warshall` was rendered from its profile
and read as the model reads it (1,671 + 1,108 tokens). Findings:

| # | Sev | Where | Finding | Status |
|---|---|---|---|---|
| P1 | **H** | `evidence/deps.py` `_classify_var` | **Every PolyBench array is labelled `[scalar]`.** Array-ness is inferred from DiscoPoP's `GEPRESULT_` name prefix, which the C kernels do not get: their dependences name the arrays plainly (`D`, `tmp`, `A`, `B`, `C`, `path`). Only the C++ applications carry the prefix. So for 30 of 37 benchmarks the digest reads "RAW on SCALARS: i, j, k, n, path — usually a reused location or an accumulator, not a value travelling between iterations", which is the opposite of the truth for the one array the kernel is about, and points the model at privatisation. | fixed — Fix 69 |
| P2 | M | `llm/request.py` task text | The task contradicts the system prompt in the default mode. System prompt (`--llm-pragmas`): "annotate it yourself… Nothing here re-profiles your code: this list is the whole judgement". Task: "after re-profiling, DiscoPoP must detect a genuinely parallel pattern". The task text does not switch with the mode. | fixed — Fix 67 |
| P3 | **H** | `llm/prompts.py` "HOW YOUR REWRITE IS CHECKED" | **The prompt describes a gate that is not the one running.** It lists a timing step ("has to be faster") that is off in every arm (`--no-require-speedup`); it says "byte for byte" where a measured numeric tolerance applies; and it omits two checks that do run — the schedule matrix and the perturbed input. A model told its loop must beat one thread at the profiling size has reason not to parallelise at all. | fixed — Fix 67 |
| P4 | **H** | `llm/render.py` loop structure | **At the profiling size every loop is branded "too fine-grained on its own".** The marker compares iterations per activation against ~1000; the agent profiles at SMALL/MINI (32 here), so all three loops of the kernel carry it, and the system prompt says to annotate "the outermost one that qualifies" — none does. The result is judged at a size where the same loop has thousands of iterations. The marker is only meaningful when the speed check will really run at this size. | fixed — Fix 67 |
| P5 | M | evidence listing | Noise ahead of signal: dependences on the induction variables `i`, `j`, `k` (which the prompt itself calls never the blocker) and on the parameter line (`422→414`, the function signature) are listed at the same weight as the array dependence. | fixed — Fix 69 |
| P6 | M | enrichment | Not given, though derivable: **which array elements are read and which written** (`writes path[i][j]; reads path[i][j], path[i][k], path[k][j]`) — for a restructuring this is the single most useful fact, and it is one pass over the region's source. | fixed — Fix 69 |
| P7 | M | enrichment | Not given, though DiscoPoP has it: **what is already parallelisable inside the region.** A function region containing loops DiscoPoP already reports as Do-All shows the model none of that, so it may rewrite what needed only a pragma (seen: kernels inlined into `main`). | fixed — Fix 69 |
| P8 | L | enrichment | The region's measured share of runtime is known to the planner and absent from the prompt. | fixed — Fix 69 |

## What the review did NOT find

Stated because a review that only lists defects says nothing about the rest.

* **Fast refresh translation** (`profiling/fast_refresh.py`): the sequence alignment with the independent position cross-check holds up; anything untranslatable is dropped, never guessed. The known gap — observed dependences on rewritten lines cannot be carried — is covered by the full re-profile before Phase B and, in the default mode, never decides anything (the gate does).
* **Depth** (`--restructure-depth`): regions created by a rewrite enter at depth+1 and are restructured only while `depth <= --restructure-depth`; at the default 0 they are still annotated in Phase B. The full-re-profile-at-a-depth-boundary rule costs nothing at depth 0. With Fix 73 the covered span is now right at depth ≥ 1 as well.
* **Settle**: rebuild-by-reapplying, newest-pragma-first repair and full revert all behave as documented once it uses the same tolerance as the gate (Fix 66).
* **Identity across re-profiles**: content fingerprints, not region ids, are used everywhere they matter.

## Consequence for measurements already taken

* `pilot2` and `local_obs1` ran before Fixes 64–73. They remain valid as records of that configuration and are **not** comparable with anything run afterwards; no thesis number is drawn from them.
* No E-experiment has been started, so no result is affected. Had E1–E11 run on the old code, the `no_evidence*` arms (P9), the `--no-fast-refresh` arms (F16), the `--no-llm-pragmas` arms (F17) and `full_no_hotspots` (F12) would each have carried a confound of their own.

## End-to-end verification of the reviewed agent (2026-09-18)

Sonnet, `--edit-mode direct`, campaign flags, calibration programs; full record in the
harness (`THESIS_EXPERIMENTS.md`, run log `e2e_review_2026-09-18`). Eleven configurations
in all, every one exit 0, every attempt in `candidates.jsonl`:

* `calib/prefix` (a true recurrence) under `full`, `discopop_gate`, `--no-llm-pragmas
  --no-fast-refresh`, `--evidence none`, `--restructure-depth 1`, `--no-hotspots`,
  `--no-llm-pragmas --llm-recon`, `--require-speedup`: the failure paths — `clause`,
  `correctness` at a fixed thread count, `correctness` on the perturbed input, `schedules`
  (a segfault at 4 threads), `tsan` on DiscoPoP's own pragma — all reached and all recorded.
* `calib/privtemp` (privatisable) under `--no-llm-pragmas --no-fast-refresh`,
  `--restructure-depth 1`, `--no-llm-pragmas --llm-recon`: the keep paths — a pragma-free
  rewrite exposed, annotated by Phase B and kept by Settle (F20's path); a depth-1 full
  re-profile with re-measured runtimes and a correct "nothing left" (F21); a reverted
  attempt restoring source, profile and measurements (F17), then reconstruction claims
  resolved and the rewrite kept.
* A two-file project under `full`: the multi-file path end to end (Fix 74), and the nested
  loop no longer attempted (F19).

Three things the runs themselves turned up were fixed on the spot: the O(n²) recomputation
the contract invited (P13, Fix 77), the calibration programs' idempotent repeat loop (a
model with no evidence did all the work in the last repetition; harness generator v3), and
included units losing their clauses in the explorer's AST matching (Fix 78).
