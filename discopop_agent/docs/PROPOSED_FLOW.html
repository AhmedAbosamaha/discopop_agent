DiscoPoP agentic controller · proposed architecture

Restructure, Then Annotate

Today the agent interleaves rewriting code and inserting pragmas, so every pragma it adds invalidates the profile the next decision depends on. Splitting those into two phases — all restructuring first, all annotation last — dissolves the staleness, the duplicates, and the depth problems at once.

The goal, as a measurable outcome

The final source carries the DiscoPoP pragmas that actually work, and there are more of them than DiscoPoP achieves on its own. Success is P_final > P₀, with the program still correct and no slower.

Both sides counted the same way. P₀ is not "patterns DiscoPoP claims" — it is patterns whose generated pragma passes the clause check and compiles, exactly the bar the run's own output has to clear. On example4 DiscoPoP claims one applicable pattern, and it is private(ok) on the sortedness check: a pragma that compiles into a program reporting success even with the sort deleted. Counted honestly, that baseline is 0, not 1 — and scoring the baseline generously while scoring the result strictly made every run look like a regression when it was a tie.

The flow

The source stays pragma-free for the whole of Phase A. Nothing writes a pragma until every rewrite is settled — which is what makes the second phase able to work from a single, trustworthy profile.

When we profile

Three points, and only three
WhenWhat it is forCost
before the agent establishes .discopop/ and P₀, the number of applicable patterns DiscoPoP finds unaided you run it
after each kept rewrite the only way to learn whether the rewrite exposed anything; also refreshes the candidate queue ≈15 s each
never in Phase B all pragmas come from the single profile taken after the last kept rewrite free

This is the change that fixes the staleness. Today a Tier-1 pragma is applied without re-profiling, so every queued patch targets a file that has already shifted — which is what left patch hanging on an interactive prompt. Here, nothing is profiled while pragmas are being inserted, and each patch is re-derived from the pragma text and its anchor against the current file rather than replayed from a stored diff.

When we check, and for what

Each gate asks one question; nothing is asked twice
CheckPhaseAsksRuns
Gate AA is this rewrite harmless? compiles, and prints byte-identical output apply · compile · correctness
pattern countA did the rewrite expose parallelism DiscoPoP can use, in the lines it changed? no build — a count from the fresh profile
clause checkB is this pragma's data sharing even legal? static; nothing executes
Gate BB does this pragma work? apply · compile · openmp · tsan · correctness
final checkend is the finished program correct and no slower than what the user started with? one build, one run per recorded input, timing

Phase A never runs ThreadSanitizer or timing — a pragma-free rewrite is single-threaded, so both questions are meaningless there. They belong to Phase B, where a real pragma exists.

How the speedup is measured

Nothing here runs unless --require-speedup is on. When it is, speed is asked at exactly two moments, and they answer different questions.

Step 0 · calibrate, once per run
WhatHow
noise floor Build the current source ONCE, then time that one binary against itself in alternating pairs. Every ratio should be 1.000; it is not. On this machine an unchanged example4 measured between 0.947 and 1.020. The keep threshold is set just below the worst median observed, so jitter alone can never discard a pragma.
Step 1 · per pragma, in Phase B
MetricComparesAnswers
marginal state against state + p — the file as it stands versus the same file with this one pragma added. Both built -O2 -fopenmp, timed in interleaved pairs, median of the per-pair ratios. This is the per-region speedup. What the pragma is worth in the program it will actually ship in — not in isolation.
scaling state + p at OMP_NUM_THREADS=1 against unrestricted — the same binary, run two ways. whether it parallelizes at all, or only adds barrier cost

Why both sides are -fopenmp. An earlier version compared an OpenMP build against a non-OpenMP one. That flag changes codegen and layout on its own, so part of every difference came from the compiler rather than the parallelism — the same pragma on the same case measured 0.89× and 1.10× on consecutive runs. Building both sides the same way and changing only the pragma keeps the compiler out of the ratio.

Why interleaved pairs and a median. Whatever the machine was doing during a pair affected both halves of that pair, so the ratio survives load drift. The median then discards the outliers a single slow run would otherwise create.

Step 2 · once, on the finished file
MetricComparesAnswers
net the finished source against the ORIGINAL program's wall time, recorded before anything was touched did the whole run leave the user better off? Every per-pragma verdict can pass while this still fails — that is not a contradiction, it is why the check exists

The keep rule. Faster → keep. Within the measured noise floor → keep, because the region may be hot on other inputs and it costs nothing. Measurably slower → drop. That discards a pragma on 513 trivial stores while keeping every pragma too small to measure — which is what the goal, more working pragmas, asks for.

With the flag off, none of the above runs: no calibration, no marginal, no scaling, no net check. Every safe pragma is kept and nothing guards against ending up slower.

When we revert, and when we write

Every gate runs on a temporary copy, so a failing check never touches your source. There are only two writes, and each happens after its own check has passed — plus the settle step, which can undo any of them.

Why settle re-gates rather than trusting the rebuild. Every earlier gate judged a candidate patch applied to a temporary copy. The file that ends up on disk is a reconstruction — the survivors re-applied onto the original — and that is not the artifact any gate looked at. Skipping this step is how a pragma the gate rejects deterministically ended up in a real source file.

Depth > 0

Depth now exists only in Phase A, and Phase A has no pragmas in it. That is what makes the old depth problems disappear rather than get managed.

Broke at depth > 0 beforeUnder the split
pragma validation deferred gone — terminal has nothing to defer, because no pragma is validated in Phase A at all
LLM handed parallelized code gone — the source is pragma-free for the whole of Phase A
duplicate pragma proposals gone — DiscoPoP is never re-profiled on a file containing its own output
stale patches from line shifts gone — the only writes in Phase A are rewrites, and each is immediately followed by a re-profile
context-line pragma flips the gate gone — no pragma exists anywhere in the file, so it cannot appear in a diff's context

What still has to work, and does: region identity across rounds is content fingerprints, as today — and it gets easier, because the only text that changes is a rewrite, which is meant to change identity, rather than a pragma insertion, which is not. Termination is unchanged: new regions enter at depth + 1, and after --restructure-depth rounds none qualify.

One new risk, and it grows with depth. Every round can leave the code slower sequentially — odd-even transposition sweeps the full range where bubble sort shrank, costing about 22% before any threading. Phase B then measures each pragma against that restructured baseline, so every marginal gain can look fine while the final check, which compares against the ORIGINAL, still fails.

When that happens, bisecting the pragmas is aimed at the wrong thing — the cost is in the rewrites. So the rollback unit has to be a rewrite together with the pragmas inside it, unwound in reverse order of application. A rewrite that needs its own pragma just to break even is worth less than no rewrite at all.

The riskiest combination is therefore --restructure-depth > 0 with --no-require-speedup: more rounds accumulating serial cost, and no final speed check to notice. If you raise depth, leave the speedup gate on.

Dropping rewrites that earned nothing

A Phase-A rewrite exists to make DiscoPoP able to parallelize something. If Phase B applied no pragma to any region it exposed, it achieved nothing — and it is not free: odd-even transposition sweeps the full range where bubble sort shrank. A rewrite stays only if it has pragmas. Being incidentally faster on its own does not save it.

Justification is by identity, because regions nest and line spans drift
CaseVerdict
pragma on an inner loop, inside an outer rewrite outer rewrite justified — it exposed that loop
nested rewrites, one pragma inside both both justified; each genuinely contributed
pragma on a region DiscoPoP could always parallelize justifies nothing — no rewrite enabled it
rewrite built on top of a dropped rewrite its patch fails to apply on the rebuild — dropped too, and reported

Rebuild, do not un-apply. The file ends as original + r₁ + r₂ + … + pragmas, so reverting one rewrite in place means reversing a patch that later changes were written on top of. Instead, re-apply the survivors onto a fresh copy of the original: nothing is ever reversed, and dependence is discovered rather than computed — a change that stood on a dropped one simply fails to apply, which is the signal that it goes too.

This is also the rollback unit the depth > 0 problem needs: a rewrite and the pragmas inside it travel together, because dropping the rewrite makes its pragmas fail to apply.

What this does not solve

Phase B validates each pragma against a file accumulating the others, so a late failure can be an interaction rather than that pragma's own fault — the bisect at the end exists for exactly that. And the Phase A criterion, "a pattern appeared", is weaker than "a pragma works": DiscoPoP will report a do_all for a loop whose generated pragma cannot compile, so a rewrite can pass Phase A and still earn nothing. The rebuild catches it, but only after the LLM call and the re-profile have been spent.
