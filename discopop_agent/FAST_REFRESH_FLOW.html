Dependences Without the Run

Re-profiling after every rewrite costs 8–12 s, and the part that scales badly is the instrumented run — 17× native on a 104M-operation kernel. Everything else DiscoPoP needs is static. So skip the run and translate the previous one’s observed dependences onto the new code instead.

On a tiny program the explorer dominates and skipping the run saves 4%. On a compute-heavy one the run dominates and skipping it saves 64% — and that multiplier grows with memory traffic, so the saving is largest on exactly the programs that are most painful to profile.

The translation is the part that can go wrong quietly

DiscoPoP numbers instructions from a single counter in module order, so an edit renumbers everything after it — verified: an edit inside bubble_sort diverged the numbering at instruction 19 and renumbered all of main behind it. A dependence re-pointed at the wrong instruction does not fail; it silently misinforms the analysis. Four things had to be got right.

  • The obvious key does not work. instructionID_to_lineID_mapping.txt maps an instruction to file:line:col, but many-to-one — ids 3, 6, 9 and 12 all map to 1:6:0 — so it cannot be inverted. And about a fifth of instructions (36 of 178) have no position at all.
  • What works is alignment. Both files are the same program’s instructions in order, so old and new are aligned as sequences after rewriting the old positions into new-line coordinates. Positionless entries then match by context, the way a blank line does in a text diff. Instructions in rewritten code are given a token that can never match.
  • 67@43 is not line 43. The number after the @ is callpath state — instruction 67 sits at line 11 — and parser.py strips it before use. So the instruction id is translated and the state travels untouched.
  • Static dependences live in the dynamic file too, written with a bare instruction id and an S- memory region (50 of 114 lines here). They are dropped rather than translated: the compile has just regenerated all of them, and the explorer reads that file separately.

Also verified, and load-bearing: instruction numbering is deterministic — two compiles of the same file produce byte-identical mapping files. Static memory-region ids are not (S-1208730495 vs S-1084334991 for the same variable), so nothing here matches on them; DiscoPoP’s own map_static_and_dynamic_dependencies() matches those by variable name.

The gap, and who fills it

Dropping what cannot be translated leaves rewritten code covered by static dependences only. Static analysis reports a dependence whenever it cannot prove there is none, so a freshly written loop is usually blocked by something that does not actually happen — and there is no dynamic data for new code to settle it.

That matters precisely because a rewrite creates new regions, and at depth > 0 those are the regions the agent is supposed to parallelize. Left alone, static caution would keep them sequential forever.

--llm-deps lets the model discharge them, and it is worth being plain about what that costs. Everywhere else the agent treats DiscoPoP’s analysis as ground truth; this is the one place a model’s claim is allowed into it. A wrong SPURIOUS produces a racy loop.

Two rules keep the question narrow, and both were learned by getting them wrong first. Only DiscoPoP’s own Do-All blockers are reviewed — the first version asked about every static dependence in the rewritten lines, 76 of them on example4, of which 37 were induction variables and 3 were body-locals that the agent already knows are never blockers. It discharged 70 of 76, with at least one visibly wrong justification. Asking a model forty questions whose answers are already known is how it learns to answer carelessly; targeted at blockers, the same run asks zero and reaches the same result. And only static-origin blockers are reviewable: a dependence DiscoPoP actually observed is not up for discussion.

What contains the rest: the model is told to answer REAL when unsure, since a dependence wrongly called real costs only a missed parallelization; every judgement is written to llm_deps.json; discharged dependences are matched back to the exact lines that produced them and the explorer re-run, restoring the original analysis if it then fails; and a pragma resting on one still has to pass ThreadSanitizer, the byte-identical output check, and the speedup gate.
